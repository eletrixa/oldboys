# Unit: hosted apply page (`/apply/<tag>` + `POST /api/apply`)

The URL we put into LinkedIn Jobs "apply on external website", Jobs.cz and StartupJobs ad text. Public, candidate-facing: calm, short, no mention of research.

## Page
- `params.tag` → `IntakeTag.safeParse`; `SELECT role, company FROM intake_tags WHERE tag = ?` via `getCloudflareContext()`; miss → `notFound()`. The page is the one place an unknown tag shows (on purpose: a mistyped ad link should say so before anyone fills it in); the API answers an unknown tag like a known one.
- Metadata (`generateMetadata`; the root layout's product title and description never reach a candidate): title "Apply: <role> at <company>" ("Apply: <role>" without a company), description "Send us your LinkedIn profile or CV. We reply by email.", the same for Open Graph, `alternates.languages` for en and cs. Favicon: `src/app/apply/icon.svg` (a neutral sheet, not the product mark).
- Language: English by default, Czech with `?lang=cs` (the Jobs.cz ad link); a "Česky" / "English" link at the top switches; `<main lang>` carries the language; the form posts to `/api/apply?lang=cs` so the handler's 400 sentences are Czech too. All copy lives in `apply-copy.ts` (`COPY[lang]`); both languages have the same keys (tested).
- Eyebrow "Apply"; heading: the role; under it "at <company>" when the tag has one (`intake_tags.company`, set in the `/intake` tag form or `POST /api/intake/tags` `company`); sub copy: "Send us your LinkedIn profile or CV. We read every application and reply by email." Fields: Full name (required), Email (required), LinkedIn URL (optional), CV (optional, see "CV uploader"), Message (optional textarea), honeypot `hp_contact` (`HONEYPOT`; visually hidden, `aria-hidden`, `tabIndex=-1`, `autoComplete="off"`, labelled "Leave this empty": no name or label an autofill heuristic maps to a person's data, as `website` was) and the milliseconds from the form's first render to Send as `fill_ms` (`FILL_MS`). The LinkedIn field has `autoComplete="off"` (`url` made the browser offer a personal site). Client rule: LinkedIn URL or a CV (file or pasted text) required, and an older `.doc` counts only beside LinkedIn (it is stored, never read); a LinkedIn URL that `normalizeLinkedinProfile` rejects is an error (otherwise the funnel would store `incomplete` and the candidate would still see "Received"). All rules live in `apply-fields.ts` (`checkApplyAll` / `checkApply`, sentences from `apply-copy.ts`; `MESSAGES` is the English set); the handler runs the same function.
- Privacy line under the send button: "<Company, or 'The hiring company'> uses what you send only for this application and deletes it from this service after 7 days." (retention = `RETENTION_DAYS`, the purge's) and a "Privacy notice" link opening `/apply/<tag>/privacy` in a new tab (the draft stays). The notice says who decides (the employer; the page is run for them by a hiring service provider), what is collected (what the candidate sends, plus public professional information read to prepare the interview), what never is (Art. 9 data, personality scores; a person reads every application), why (Art. 6(1)(b) pre-contract steps and Art. 6(1)(f), as in the audit record), how long (7 days, earlier on request) and the rights (reply to our email; ÚOOÚ). `noindex`.

Phone first: 16px gutters, every control ≥ 44px tall, no horizontal scroll at 360px.

## CV uploader ("just works")
The one component candidates fight with elsewhere, so it is specified in detail. Client in `apply-form.tsx`, `cv-field.tsx` and `cv-drop.tsx` (each under 150 lines), pure helpers in `apply-fields.ts`.
- **Formats**: PDF, Word (`.docx`) and plain text (`.txt`), up to 10 MB (`CV_MAX_BYTES`), read; an older Word `.doc` (binary, no bundled parser) is accepted for storage only: its row says "We keep older Word (.doc) files but cannot read them, so we need your LinkedIn profile too. A PDF or .docx works on its own." and Send without LinkedIn answers "We cannot read older Word (.doc) files. Please add your LinkedIn profile too, or attach the CV as PDF or .docx." Accepted by extension or media type (`isCvFile` / `cvFileProblem` in `apply-fields.ts`, built on the domain `cvKind` in `cv-kind.ts`); images and other formats get "Please attach your CV as a PDF, Word or text file." The `<input type=file accept>` lists exactly those four (`CV_ACCEPT`).
- **Picking**: a drop zone that is also the browse button (one `<button type=button>` whose accessible name is "Choose a file or drop it here", keyboard reachable, `aria-describedby` the format/size line) next to a visually hidden, unnamed file input; drag-and-drop on the zone (`dragenter/dragover/dragleave/drop`, highlighted while a file is over it, `prefers-reduced-motion` respected). A file dropped anywhere beside the zone is swallowed instead of opening in the tab (the draft would be lost): `useNoStrayDrop` (`stray-drop.ts`) is mounted by `cv-field.tsx`, so it holds in paste mode too. Several files dropped at once: the first usable one is attached (`pickDropped`) and a line under the zone says "Only one file can be attached, so we took cv.pdf.". An empty (0-byte) file is refused like a wrong type ("That file is empty. Please attach your CV again.", `cvFileProblem` → `"empty"`). Dropping or picking a second file replaces the first; a refused file never replaces a good one, and then the sentence names both ("photo.png was not added: please use a PDF, Word or text file. scan.PDF is still attached.", `cvRefusal`) while the zone keeps its neutral border (red only when no file is attached). A chosen file is shown as a row: name, size ("1.2 MB"), kind, and a "Remove" button (≥ 44px) that hands focus back to the zone. Type and size are checked the moment the file is chosen, inline under the zone, before anything is sent.
- **Paste instead**: a quiet toggle "No file at hand? Paste your CV text" reveals a textarea (`cvText`, ≤ 20 000 chars, `CV_MAX`, with a live "N of 20,000 characters" count and no `maxLength`, so a long paste is refused with a sentence, never silently cut), hides the zone; "Attach a file instead" goes back. The visible mode decides what the form sends (the file in file mode, the text in paste mode); the server still lets a file win if both arrive.
- **Sending**: `XMLHttpRequest` (not `fetch`: it has no upload progress) posting the multipart body; a progress bar (`role=progressbar`, aria-valuenow, aria-valuetext) under the button with "Uploading 43%", then "Checking your CV" after 100% until the response ("Checking your details" when no CV was sent); the button reads "Sending…" and is `aria-disabled` (not `disabled`: it takes focus at Send and keeps it); the fields sit in a `<fieldset disabled>` while sending, so nothing can be edited that would not be sent (the body is built from the draft taken at Send, `applicationBody`, never from the live form); the form stays filled. One send at a time: a synchronous `useRef` guard set before the POST and cleared when it settles, so a double tap or a tap plus Enter sends one request. Timeout: 90 s of silence (`POST_IDLE_MS`, restarted by every upload progress event and once the upload ends), never a limit on the whole send, so a 10 MB CV at 0.5 Mbps finishes. On a network error, a timeout or a 5xx: the error sentence above the button, and the one send button reads "Try again" and resubmits the same draft; nothing is cleared. The status-to-sentence mapping is `replyOutcome` in `apply-fields.ts`.
- **Done**: `role=status` card "Received. We'll reply to <email>." (the heading takes focus) with one line that names what was attached (`attachedLine`: "Your CV: jana-cv.pdf" / "Your CV, pasted as text" / "Your LinkedIn profile", joined with ", and your LinkedIn profile" when both), "We usually reply within a week." and "You can close this page." It appears only for 201, and the handler answers 201 only once the application is stored. The 200 the handler gives a bot (honeypot or fill time) is "We could not send your application. Please try again in a moment." with Try again on our page, and the honeypot is cleared, so a candidate whose browser filled the trap is never told an unstored application arrived and gets through on the retry. No run, id or status ever reaches the candidate. 400 → the handler's own sentence (no retry). Anything else (5xx, the in-flight 503, a platform 429) → "We could not send your application. Please try again in a moment." with Try again: never a rate-limit sentence.
- **Errors**: `checkApplyAll` returns every `{field, message}` in form order; Send marks all of them at once (`aria-invalid` and the sentence under each field), the first gets focus and is the one `role=alert` (server and network sentences above the submit button; a client error clears a stale server sentence). Name, email and LinkedIn are checked again on blur when filled (or already marked), and a marked field clears as soon as it is fixed. Never a browser-native validation popup (`noValidate`).

## Server
- `cvText` form field accepted (trimmed, ≤ `CV_MAX`), mapped to `IntakeInput.cvText`; a file and text together → the file is stored and the text ignored (`cvText` is neither checked nor used when there is a file).
- `isCvFile` in `checkApply` mirrors the formats above; the handler runs the same check (400 with the same sentence, in the language of `?lang`).
- The handler reads the file's text itself (`extractCvText`) before it answers: a PDF, DOCX or TXT without readable text and no LinkedIn → 400 "We could not read any text in that PDF. Please add your LinkedIn profile or paste the text of your CV." (Word / text-file variants), nothing stored, the file stays attached in the form; with LinkedIn it is stored and noted. The extracted text goes to the funnel as `cvText`; when there is none (LinkedIn beside it), the reason goes as `cvNote` and the funnel stores it without parsing the file again. The file goes to the funnel under the canonical media type of its kind (`CV_MEDIA_TYPE`), so a typeless `.docx` is never stored or parsed as the `toCvFile` PDF default.
- `src/domain/cv-kind.ts`: `cvKind(file) → "pdf" | "docx" | "txt" | "doc" | null` by media type or extension (PDF first, as `isPdf` always did), `isPdf` (moved here from cv-text), `CV_MEDIA_TYPE`, and `sniffCvKind(bytes, declared)`: the kind the bytes' magic names (`%PDF-`, the ZIP local header `PK\3\4`, the CFB header of a `.doc`), else the declared one. The handler and `extractCvText` use it, so a `.docx` sent as `application/pdf` is read and stored as Word, and a `.doc` renamed `.docx` still needs LinkedIn. `src/domain/cv-text.ts` dispatches on it; DOCX text via `mammoth` (`extractRawText` with `buffer` for its Node entry and `arrayBuffer` for its browser entry, on a copy; whitespace-collapsed, ≤ `CV_MAX`), bytes must start with the ZIP magic `PK` ("not a Word file (no ZIP header)"); a library error or empty text becomes a note like the PDF path ("Word file has no readable text", "Word file could not be read: …"). `src/domain/cv-inflate.ts`: before a parser runs, `zipInflateProblem` (every ZIP entry) and `pdfInflateProblem` (every non-image stream; encryption or an LZW / chained filter cannot be measured and is refused) stream the data through `DecompressionStream` and count; past `CV_INFLATE_MAX` (40 MB) the file is not parsed and the note says so ("Word file would inflate past 40 MB, not read"), so a crafted 9 MB file cannot exhaust the Worker's memory or CPU. Text files: UTF-8, UTF-16 by its BOM, or windows-1250 when the bytes are not UTF-8; more than 1 % control characters or U+FFFD (a binary file renamed `.txt`, UTF-16 without a BOM) is "CV text file is not readable text". The email connector still picks only PDF or text attachments.

## Handler
```ts
export async function handleApply(request: Request, env: IntakeEnv, now: Date): Promise<Response>
```
1. `rejectCrossOrigin(request)` from `src/app/api/_lib/same-origin.ts` (the shared browser check from plan 009: Sec-Fetch-Site same-origin and Origin matching Host) → 403 `{error: "browser only"}`.
2. `env.APPLY_RATE_LIMIT.limit({key: CF-Connecting-IP})` (wrangler `ratelimits`, 5 a minute; optional in the type so unit tests may leave it out) → 429 `{error}` with the retry sentence, before the body is read.
3. No `Content-Length` (a chunked body; browsers and `curl -F` always declare one) → 400 `unreadableForm`; a declared length over CV limit + 256 KiB → 400 before buffering. `request.formData()` (parse failure → 400); `hp_contact` non-empty, or `fill_ms` missing, not a number or under `MIN_FILL_MS` (3000) → 200 `{received: true}` (silent drop; nothing stored).
4. Validate (`checkApply` once; it owns the `z.email()` check): `tag` IntakeTag, `name` 1..200, `email` z.email, `linkedinUrl` ≤ 500 optional and a valid LinkedIn profile URL, `coverLetter` ≤ 10000 optional, `cvText` ≤ 20000 optional, `cv` File optional: size ≤ 10 MiB (`CV_MAX_BYTES`), PDF / DOCX / TXT by media type or name (`isCvFile`) → else 400 `{error}`. LinkedIn or CV (file or text) required → 400.
5. `externalId = sha256Hex(`${tag}|${email.toLowerCase()}`)` (one application per email per position; a resubmit is a duplicate; one with other details than the stored row is answered the same and leaves a `resent ...` note on the row for the operator, see funnel.md).
6. `ingestApplication({ source: "apply-page", ... }, env, now)`.
7. Response: `received` (a duplicate whose first send is still being stored, or a retry that lost the claim on a failed row) → **503** `{error}` with the retry sentence, so "Received" never shows before something is stored; anything else (new, duplicate, unmatched, `capped`) → **201** `{received: true}`, the same code for a duplicate so the status cannot reveal that an email already applied (the honeypot is the only 200). A capped application is queued, not refused: the funnel's cron pass (`retryCappedApplications`, every 15 minutes) starts its run once the hour has room. A funnel failure → 500 `{error}` with a plain sentence, details to `console.error` only; the funnel marks the row, so the candidate's Try again resumes it at once (CV stored, run started or linked). Never return applicationId, status or runId.
