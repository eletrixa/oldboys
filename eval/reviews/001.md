Evidence: wireframes (discord.png, discord2.png), live local run screenshots for "Jozef Buryan, Praha" (buryan-1..4), collector reports pokorny2.txt and buryan2.txt, and the code listed in the brief. The missing ANTHROPIC_API_KEY is not penalised itself; what the user sees when it is missing is.

Note: the screenshots predate two code changes (the cost line in the header and platform-first lineup sorting). Where the code fixes a screenshot problem, the score credits the code.

**Overall: 2.3 / 5 stars** (weighted mean 2.325).

## What works

- Screen 1 is a near pixel match of the wireframe: same heading, sub copy, two-column fields, helper lines, privacy box, CTA and "Usually takes 2 to 4 minutes".
- The pause-and-ask loop is real. The Workflow pauses on `step.waitForEvent`, the UI asks one question at a time (capped at 3), and the answers go back in one event.
- The FACT gate is deterministic first (quote must be in a supporting excerpt), then a second model on the residue. Protected categories are filtered at extract (prompt) and at synthesize (regex plus model).
- Every hiring step has an `onEmpty` gap, so in principle nothing disappears silently.
- Cost is tiny: about one cent of Apify per run.

## What is broken, by criterion

**1. Screen 1 (4.0).**
- The privacy line says "deleted after judging". That is jury language, not HR language, and nothing backs it: no scheduled purge exists, and `expires_at` is written but never read by a job.
- The footer says "Sample content only during development." It undermines trust on the demo screen.
- The form reads `NEXT_PUBLIC_RUN_TOKEN`. If set, the bearer token ships in public JS. If unset in prod, every submit gets a 401 and the user sees "please check the details", which blames them.
- No placeholders, unlike the wireframe. All 4xx and 5xx collapse into one message.

**2. Screen 2 (2.5).**
- First paint is "Found 0 public mentions" with a spinner and an empty bar. That reads as failure. The bar then sits at 20% for the entire lineup phase.
- The lineup in the wireframe is profiles (LinkedIn, GitHub, X). The live lineup is 12 web pages: rejstrik.penize.cz twice, cc.cz twice, myheritage.pl, firmy.cz, fakturujzdarma.cz. Every avatar is "JB", so rows are indistinguishable.
- The three questions were spent on facebook.com, pravednes.cz and cc.cz. The one high-value row, "LinkedIn, Josef Buryan, CMO Groupon", was never asked and stayed "Not sure yet".
- After the third answer there is no "thanks, continuing" state. `sendAnswer` ignores the HTTP result, so a failed POST leaves the run paused forever with no message.
- On failure, the progress rows vanish and are replaced by "Something went wrong while putting this brief together. Please start a new one." No reason, no partial result, no retry. "See the brief" stays disabled forever.
- "You can leave this page. We will let you know when it is ready." There is no notification channel. The copy is false.

**3. Breadth (3.0).**
- All 16 collector steps in `hiring.ts` were attempted in both reports. Buryan returned nothing from GitHub, Stack Exchange, Hugging Face, ORCID, OpenAlex and Bluesky, which is plausible for a marketing executive. TikTok was never requested. For Pokorný, LinkedIn, X and TikTok had "nothing to request" because no handle was merged.
- The gap reasons lie about why. "Nothing to request" is recorded as "no public TikTok profile found", which claims a search that never happened.
- The 12-call budget counts free REST fetches. Buryan's collectors alone made 14 calls and Pokorný's 12, plus the role-questions LLM call. In the real Workflow, `doStep` skips the remaining collectors once the counter hits 12, and the skip is then recorded with the `onEmpty` text, so a budget skip of the website crawl becomes "no personal site found". The collector reports come from a harness that does not apply this gate, so they overstate what a real run collects.
- A Facebook profile was found in SERP, but no Facebook step exists. Czech trade registry hits are in the lineup, but the hiring recipe never reads them properly.
- Collectors run strictly in sequence. Pokorný's collectors alone took about 173 seconds before any LLM step. The 2 to 4 minute promise is at risk once extract, verify and synthesize run on Opus.

**4. Identity (1.5).** This is the most serious gap. The brief's core requirement is that namesakes are never silently merged.
- The deterministic fallback in `resolve.ts` scores 0.85 (merge) whenever the anchor appears as a substring of the excerpt. With "Praha" as anchor, that is close to name-only matching.
  - Buryan: elib.nlb.by, a Belarusian library search page, was merged at 0.85.
  - Pokorný: chanceliga.cz (a footballer), an irozhlas.cz tag page, a radio.cz transfer story and an Instagram account were all merged at 0.85. The subject is a footballer namesake unless the user really meant the footballer.
  - The screenshot shows rejstrik.penize.cz "This is them" auto-merged. The same lineup has two different trade-licence numbers (IČO 03065405 and 17659043) for "Josef Buryan", which means at least two people. No contradiction is raised.
- After resolve, collectors that have no merged handle fall back to a name search. GitHub, Stack Exchange, ORCID and OpenAlex results are then stored as sources for the subject without any identity check. For Pokorný this attributes github.com/pokycek, a Stack Overflow user, an ORCID record and an OpenAlex author (likely Lukas K. Pokorny, the Vienna religious-studies scholar) to the same person. This problem does not depend on the LLM key.
- `extract.ts` excludes only sources whose URL was explicitly rejected. Everything "possibly-same-as", every unanswered row and every name-search hit flows into extraction.
- What is good: there are three decisions, the user is asked when unsure, and "I'm not sure" is kept as possibly-same-as rather than coerced.

**5. Honesty and safety (2.5).**
- Good: there is no person scoring, and the FACT gate and protected-category filter are both in code with tests.
- Bad: the failure is opaque. The ledger has the real reason, but the UI shows a generic apology.
- Gap reasons misstate whether a source was searched (criterion 3).
- The deletion promise has no purge job behind it.
- "This is them" is shown as settled on a heuristic substring match, with no reason visible to the user.
- The new run view has no CACHED or MOCK labels, although the binding decisions require them.

**6. Judge value (1.5).** Today a hiring manager gets nothing: three questions about junk websites, then an error. Even with a key, the lineup feeds namesake data into extraction, so the brief would contain confidently sourced facts about other people. That is the worst outcome a jury testing namesake handling can find. No degraded "evidence only" brief exists for when the AI step is unavailable. That would turn the current dead end into a demo.

## Top 10 fixes, ranked by impact

1. **Never fail the run on an LLM seam error.** In `src/recipe/seams/extract.ts`, catch the `ports.llm` error and return an empty outcome with a note, as `role.ts` and `synthesize.ts` already do. `src/recipe/seams/synthesize.ts` must then build an evidence-only brief: confirmed sources grouped by step with links, every gap, and a visible line "AI summary unavailable, sources only". `src/workflow/research-run.ts` marks such runs `done` with a `degraded` flag instead of `failed`.
2. **Stop merging on a city substring.** In the `src/recipe/seams/resolve.ts` fallback, cap anchor-substring matches at 0.6 (possibly-same-as). Allow merge only on hard links: the anchor URL equals or links to the profile, a handle is cross-linked from an already merged profile, or the IČO matches. Drop non-profile web pages (registries, tag pages, library search) from candidates, or group them under "Mentions", and dedupe by host plus path.
3. **Quarantine name-search results.** In `src/recipe/sources/github.ts`, `stackexchange.ts`, `orcid.ts`, `openalex.ts`, `huggingface.ts` and `bluesky.ts`, when no merged handle exists, either skip with the gap "not searched: no confirmed profile", or emit the hits as new candidates for the lineup instead of subject sources. In `src/recipe/seams/extract.ts`, pass only SERP sources plus sources tied to merged candidates, never possibly-same-as.
4. **Make gap reasons truthful.** In `src/workflow/research-run.ts`, a budget skip in `doStep` must record "not searched: run budget reached", not the step's `onEmpty` text. In `src/recipe/runner.ts`, "nothing to request" must return a distinct flag so the gap reads "not searched: no confirmed handle". Show "searched, nothing found" and "not searched, and why" as separate groups in the brief.
5. **Fix budget accounting.** In `src/adapters/d1.ts` `loadContext`, count only paid actor calls toward `RUN_BUDGET_CALLS`, either from a `paid_calls` value in the ledger ref or by excluding `rest/*` actors. Free REST fetches currently push the website crawl and talks search over the cap in real runs. Add a test that a full hiring recipe with zero-cost REST steps reaches `talks_serp`.
6. **Ask the right questions.** In `src/app/runs/[id]/run-view.tsx`, order questions by platform value and score so LinkedIn, X and GitHub come first. Never ask about plain web hits. In `src/app/runs/[id]/parts.tsx`, replace the initials avatar with a platform mark and show the one-line reason (for example "mentions Praha", "links to LinkedIn"), as the wireframe does.
7. **Make failure visible and recoverable.** `src/app/api/runs/[id]/state/route.ts` should return `failure: {step, reason}` from the last `failed` ledger row. Map it to plain words in `src/app/runs/[id]/run-view.tsx`, for example "Writing the brief failed because the AI service is not configured." Keep the progress rows with the failed row marked, show the sources found so far, and add a "Try again" action.
8. **Fix the progress copy.** In `src/app/runs/[id]/run-view.tsx`, label row one "Searching public sources" until `mentions > 0`. Advance the bar within the collector phase by steps done out of total from the ledger. Replace "We will let you know when it is ready" with "Keep this tab open or bookmark this link". After answers, show "Thanks, continuing" and check `res.ok` in `sendAnswer`, retrying or showing an error on failure.
9. **Run collectors in parallel.** In `src/workflow/research-run.ts`, run the post-resolve collector steps concurrently, for example with `Promise.all` over `step.do` calls in batches of 4 to 6, and keep extract, verify and synthesize sequential. Sequential collectors take about 3 minutes alone, which breaks the "2 to 4 minutes" promise on screen 1.
10. **Clean up screen 1 trust and auth.** In `src/app/start-form.tsx`, remove `NEXT_PUBLIC_RUN_TOKEN`. Have a same-origin server action or route attach the token server-side, keeping the hourly cap. Map 400, 401, 429 and 503 to distinct messages. Change the privacy copy to "Collected data is deleted after 30 days" and back it with a `scheduled` handler in `src/worker.ts` that purges D1 sources and R2 objects past `expires_at`. Remove the "Sample content only during development." footer from `src/app/page.tsx`.

Also delete dead code: `src/app/runs/[id]/lineup-form.tsx` and the old `report/page.tsx` still use the legacy `{candidateId}` contract and a radio list that contradicts the wireframe.

## Verdict

Screen 1 is done and the Workflow skeleton (pause, ask, resume, ledger, FACT gate) is genuinely good engineering. As a product, though, iteration 001 fails the two things the jury will test first. A run produces no brief at all when any AI step fails, and the identity layer quietly attributes footballers, library pages, a religious-studies professor and strangers' GitHub accounts to the candidate. The breadth looks wide on paper, but gap reasons misstate what was searched, and the call budget silently cuts the last steps in real runs. To reach 4.5, fix 1 to 3 first. They turn a dead end into a defensible, sourced brief that never confuses two people. Then fixes 4 to 8 make every gap and failure explainable on screen, and fix 9 keeps the time promise. Until fix 3 lands, an extra source adds risk rather than value.
